Dr. Christina Loren Clement," styled across the filings as "President of Black USA," "2024 Presidential candidate (assumed the Presidency)," and "HH Empress Queen." Detector D9 confirms it is the only multi-signal sovereign-citizen-pattern outlier in the entire 418,098-filing corpus.

How the D9 detector isolated this pattern

D9 (shell_pattern_filings, SQL hash bbbea171aa997a1e) scores each Senate filing 0-6 against six independent sovereign-citizen markers: sovereign_client, established_govt, esoteric_terms (Annuit Coeptis / King Solomon / Empress / sui generis), self_styled_title, posted_by_llc_slashes, global_pbc_naming.

At threshold ≥ 2, only LOC Nation surfaces. At ≥ 1, the next candidates are legitimate firms (King & Spalding, Patterson Real Bird) tripping one signal incidentally.

Methodology · how the full run was executed

How data-detective works — phase by phase.

The skill pushes ETL, indexing, entity resolution, and aggregation to deterministic Python + DuckDB; it reserves the LLM for reasoning over already-filtered candidates. Every numeric claim cites a SQL query by SHA-16; every named record has an evidence card; every external source is archived. The skill is corpus-agnostic — configuration lives in a Python profile module that maps file globs to mapper functions. What follows is the actual run that produced the nine findings above.

~4 min Full corpus ingest (pyarrow bulk insert; 60× faster than executemany)
99.9% Entity resolution via deterministic bridge keys
0 tokens LLM tokens spent scanning raw documents during exploration
12 SQL-only detectors with SHA-tagged provenance per query
SHA-tagged Every numeric claim cites a query hash + provenance JSON
Portable Profile-driven — new corpus = new profile.py, same scripts
Cross-corpus In-DB joins to FARA + Congress.gov; out-of-band joins to USAspending
Multi-hop SQL D11 + D12 demonstrate three- and four-way joins

The full run, phase by phase.

data-detective is structured as eight phases mirroring Spotlight's brief → methodology → cycles → fact-check → gates → handoff arc, adapted for structured records. Each phase has its own sub-skill (or, in Spotlight's case, an external orchestrator). The audit chain is preserved across the data → OSINT handoff so that every claim in this report has a single replicable path back to the source rows.

Phase 0 · preflight

Skill discovery, corpus inventory, profile pick.

The orchestrator (data-detective SKILL.md) loaded its sub-skill registry, confirmed DuckDB + pyarrow + lxml available, and inventoried the corpus: Senate LDA JSON (2008-2025), House LDA XML (2008-2025), congressional press releases JSONL, FARA bulk (OpenSanctions DOJ mirror), USAspending DoD contract API, and the unitedstates/congress-legislators member/committee graph. The congress.py profile module declared the file-glob → mapper-function bindings.

Phase 1 · ingest

ingest sub-skill — load to columnar DuckDB.

First run took 740 s/file using executemany. Replaced with pyarrow.Table.from_pydict() → INSERT INTO ... SELECT FROM _batch: full corpus ingests in ~4 minutes (down from ~12h at 740 s/file). Output: 17 normalized tables, 2.3 GB on disk, 1.5M+ lobbying activities. The XML parser was hardened with recover=True to handle several malformed House quarterly XMLs.

Phase 2 · resolve

resolve sub-skill — bridge-key entity unification.

Senate registrant.id ↔ House senateID first segment is a deterministic bridge — 99.9% match rate measured against ~14,000 House registrant records. No fuzzy matching needed. Member rosters keyed by bioguide_id; committee assignments keyed by thomas_id. Normalized name + state + role tables materialized in DuckDB for cross-corpus joins.

Phase 3 · detect + cycles + fact-check

detect + similarity-search + external-data + evidence-cards — the analytic loop.

This is the largest phase. Three iterative cycles, each running the same loop: (a) SQL-only detector against the DuckDB index — each query SHA-16 tagged into case-trace/data-detective/anomalies/name/{ranked.csv, provenance.json}. (b) Drill into the top 5-20 candidates via ad-hoc joins. (c) Hop out-of-band to FARA / USAspending / Congress.gov to triangulate. (d) Generate evidence cards (one markdown per cited record). (e) firecrawl-archive every external source. (f) Adversarial fact-check pass.

Phase 5 · synthesis

report-drafting sub-skill — findings-report.md + report.html + evidence-map.json.

Each verified claim was written to findings.json with confidence, fact-check verdict, query-hash provenance, source list, and cross-reference IDs. evidence-map.json indexes every source record cited across findings — the audit ledger used to verify replication paths. The report-drafting sub-skill (added during this investigation) produces all three Phase 5 deliverables from a working template that enforces the design discipline used here: per-finding .path replication block, per-finding .sources strip, novelty + confidence pills, and the phase-by-phase methodology pattern that absorbs the fact-check verdict table inside Phase 3 and the spotlight-handoff outcomes table inside Phase 6.
